# 3 Реализация и проверка приложения Luma

В результате разработки получено готовое мобильное приложение Luma. Глава показывает, как требования технического задания отражены в программных модулях и какие проверки уже выполнены. Для каждой группы требований сначала рассматривается реализация, затем приводится свидетельство и указываются границы вывода. Это позволяет отделить наличие программного механизма от результата его испытания. Успешная компиляция приложения сама по себе не подтверждает полное соответствие техническому заданию.

Фактическая архитектура Luma включает представления UIKit и SwiftUI, модели представления, координаторы навигации, сервисы, репозитории и доменные модели. Отдельного слоя классов `UseCase`, упоминавшегося в ранней редакции работы, в текущем исходном коде нет. Пользовательское действие принимается контроллером или SwiftUI-представлением, передаётся модели представления, а та обращается к соответствующему сервису либо репозиторию. Зависимости основных модулей создаются контейнером внедрения зависимостей, хотя часть системной инфраструктуры доступна через singleton. Поэтому далее используются только реально существующие имена компонентов.

## 3.1 Учётная запись, профиль и сессия

Раздел связан прежде всего с FR-01 и FR-02, а также с ограничениями безопасности NFR-06. Пользователь должен зарегистрироваться, указав имя, дату рождения, адрес электронной почты и пароль, пройти проверку обязательных полей и минимальной длины пароля, войти по электронной почте и паролю и восстановить сохранённую сессию при следующем запуске. В профиле должны отображаться сведения текущей учётной записи, аватар, уровень и опыт; там же размещаются настройки Face ID и уведомлений и подтверждаемое действие выхода. Биометрическая возможность должна быть скрыта на неподдерживаемом устройстве, а неудачная проверка Face ID не должна лишать пользователя обычного входа.

Формы регистрации и входа реализованы отдельными модулями `RegistrationViewController`/`RegistrationViewModel` и `LoginViewController`/`LoginViewModel`. Проверка значений вынесена в `RegistrationValidator` и `LoginValidator`: до обращения к хранилищу проверяются обязательность полей, формат введённых данных и длина пароля не менее шести символов. После успешной проверки `AuthService` вызывает `UserRepository`. При регистрации репозиторий создаёт локального пользователя, а при входе ищет запись по нормализованному адресу электронной почты и проверяет учётные данные.

Пароль не записывается в модель Core Data. `KeychainManager` вычисляет SHA-256-хеш из пароля и индивидуальной соли, в качестве которой используется UUID пользователя, и сохраняет полученное значение в Keychain. При входе хеш рассчитывается повторно и сравнивается с сохранённым. Такой механизм соответствует требованию не хранить открытый пароль, но UUID является публичным идентификатором, а не отдельным секретом. Кроме того, результат операции Keychain не поднимается в доменный слой как типизированная ошибка, поэтому статическая инспекция подтверждает используемый способ хранения, но не всю отказоустойчивость регистрации.

Состояние входа хранит `SessionManager`. При запуске `AppCoordinator` выбирает один из трёх маршрутов: восстановление основной сессии без повторного ввода, попытка биометрической разблокировки или показ экрана авторизации. Включение Face ID выполняет `ProfileViewModel`: сначала проверяется наличие именно Face ID через `LocalAuthentication`, затем запускается системная биометрическая проверка, и только после успеха настройка связывается с текущим идентификатором пользователя. Если технология недоступна или проверка неуспешна, настройка остаётся выключенной, а обычная форма входа остаётся доступной.

Такое разделение важно для границ сессии. Сохранённый идентификатор пользователя сам по себе не заменяет биометрическую проверку, если для учётной записи включён Face ID: координатор сначала открывает отдельный экран разблокировки. При отключённой биометрии сохранённая сессия может быть восстановлена напрямую. После выхода `SessionManager` удаляет состояние активного пользователя, поэтому повторный доступ к данным проходит через авторизацию. В коде также проверяется, что сохранённый для Face ID идентификатор относится к текущей учётной записи; это предотвращает использование настройки другой локальной записи.

Профиль загружает имя, адрес электронной почты, маску пароля, состояние системных настроек, аватар и рассчитанный прогресс уровня. Изменение аватара поддерживается через системный выбор изображения и `AvatarStore`; перед сохранением изображение уменьшается. Редактирование имени, адреса электронной почты или пароля в текущей реализации отсутствует, поэтому выражение «изменение профиля» здесь относится только к аватару и настройкам. Выход выполняется после подтверждения, очищает активную сессию, возвращает пользователя на экран авторизации и отменяет ожидающие и уже доставленные локальные уведомления.

Ключевая последовательность авторизации выражена коротким фрагментом сервиса:

```swift
func login(email: String, password: String) throws -> User {
    do {
        return try userRepository.verifyCredentials(
            email: email,
            password: password
        )
    } catch {
        throw AuthError.invalidCredentials
    }
}
```

*Листинг 3.1 — Передача проверки учётных данных из `AuthService` в репозиторий*

Листинг показывает фактическую границу ответственности: модель представления обрабатывает действие экрана, сервис задаёт сценарий входа и преобразует ошибку, а репозиторий выполняет поиск пользователя и проверку хеша. Отдельный объект варианта использования в этой цепочке не создаётся.

Регистрация, вход, проверка полей и восстановление сессии прослежены статически, поэтому FR-01 имеет статус «подтверждено кодом». FR-02 подтверждено частично: загрузка профиля, аватар, настройки, условное отображение Face ID и выход реализованы, но реальный Face ID требует проверки на поддерживаемом устройстве, а изменение имени, электронной почты и пароля не предусмотрено. NFR-06 подтверждено частично из-за непроверенных отказов Keychain и отсутствия общей транзакции между созданием записи пользователя и сохранением секрета. Успешная сборка доказывает компилируемость этих модулей, но не прохождение позитивных и негативных сценариев входа.

## 3.2 Календарь и управление элементами

FR-03 задаёт пять основных разделов Luma, календарный выбор даты, сортировку элементов по времени, фильтры «Все», «Выполняемые» и «Завершённые», вычисление дневного прогресса и операции изменения, завершения и удаления собственных задач. FR-04 требует совместно показывать внутренние задачи и события календаря iOS, запрашивать разрешение непосредственно перед доступом и обновлять список после изменения EventKit либо возврата приложения в активное состояние. Внешние события должны участвовать в расписании, оставаясь доступными только для чтения.

`TabBarCoordinator` создаёт пять разделов: календарь, дневник, анализ дня, статистику и профиль. Экран календаря передаёт выбранную дату и фильтр в `CalendarViewModel`. Модель представления получает данные через `TaskService`, после чего передаёт представлению отфильтрованный список и пару значений для прогресса. При расчёте сложная задача раскрывается до подзадач: завершённые подзадачи участвуют в числителе, все подзадачи — в знаменателе. Этот же принцип применяется при фильтрации, поэтому сложная задача не скрывает состояние отдельных этапов.

Собственные элементы загружаются из `TaskRepository`, а события iOS — через `CalendarEventService`, использующий EventKit. `CalendarEventTranslator` преобразует внешнее событие в общую доменную модель `TaskItem` и помечает источник как календарный. `TaskService` объединяет оба массива и сортирует их по фактическому времени начала. Преобразование не переносит внешнюю запись в Core Data и не предоставляет методов записи в EventKit. В интерфейсе проверяется источник: редактирование системного события не открывается, тогда как для внутренней задачи доступны изменение названия, описания, важности и сложности, переключение выполнения и удаление.

Общая доменная модель упрощает визуальное объединение, но источник сохраняется как обязательное различие поведения. Внутренняя задача имеет владельца, состояние выполнения и операции репозитория. Внешнее событие выступает временным ограничением: его границы используются при отображении и автоматическом планировании, но жизненным циклом управляет системный календарь. Благодаря этому отказ в разрешении EventKit уменьшает только состав объединённого списка и не меняет сохранённые в Core Data задачи пользователя.

Обновление организовано событиями. `CalendarViewModel` наблюдает собственное уведомление об изменении хранилища задач, `EKEventStoreChanged` и `UIApplication.didBecomeActiveNotification`. Серия близких событий сворачивается задержкой 0,2 секунды, после чего список перечитывается. При отказе в доступе к системному календарю сервис возвращает пустой набор внешних событий, поэтому внутренний календарь продолжает работать.

В качестве ключевого свидетельства для раздела следует использовать экран календаря, на котором одновременно видны внутренняя задача и событие iOS, а также дневной прогресс и выбранный фильтр.

*Рисунок 3.1 — Совместное отображение задач Luma и доступных только для чтения событий системного календаря*

Рисунок подтверждает пользовательский результат объединения источников. Его необходимо сопровождать пояснением, что одинаковое визуальное представление не означает одинаковых прав изменения: контекстные действия доступны только элементам с источником `.app`.

FR-03 подтверждено кодом: найдены навигация, выбор даты, фильтры, разворачивание подзадач, расчёт прогресса и операции над собственными задачами. FR-04 подтверждено частично. Режим чтения и обработчики обновления видны в коде, однако системный диалог разрешения, отзыв доступа и фактическая доставка уведомления EventKit требуют runtime-проверки. Создание, изменение и удаление записей системного календаря в приложении не реализуются и не должны заявляться. Неперехваченные ошибки операций `toggleTask` и `deleteTask` подавляются конструкцией `try?`, поэтому информирование пользователя при сбое хранения также требует доработки.

## 3.3 Автоматическое планирование и граница 23:00

FR-05–FR-07 определяют три создаваемых вида элементов: событие с фиксированным временем, обычную задачу с автоматическим выбором интервала и сложную задачу минимум с одной подзадачей. Для элемента обязательны название, важность и сложность; задача дополнительно получает период и предполагаемую длительность, а подзадача — собственные параметры. Планировщик должен учитывать внутренние задачи и системные события, исключать пересечения и по возможности помещать важные и сложные дела раньше. FR-08 задаёт преимущественный рабочий диапазон 08:00–23:00 и требует спрашивать согласие пользователя перед переносом остатка задачи на следующий день.

Выбор вида элемента хранит `AddTaskFlowViewModel`, а формы собраны в модуле `AddTask`. Для события используются введённые пользователем начало и конец: оно сохраняется без автоматического переноса и затем рассматривается как занятый интервал. Для обычной и сложной задач `TaskService` сначала получает внутренние элементы за период, затем добавляет считанные из EventKit интервалы и передаёт общий набор алгоритмам из `TaskScheduling.swift`. Введённая длительность нормализуется минимум до 15 минут при вычислении плана.

`TaskAutoScheduler` строит рабочие интервалы каждого дня с 08:00 до 23:00, вычитает пересекающиеся занятые отрезки и формирует допустимые кандидаты. Оценка кандидата учитывает день периода, загруженность, важность, сложность и более раннее размещение. Выбирается кандидат с максимальной оценкой. Если внутри рабочих сегментов подходящего окна нет, применяется `nextNonOverlappingStart`, который сдвигает начало за пересекающиеся интервалы.

Коэффициенты оценки не следует представлять как универсальную оптимизационную модель. Это детерминированная эвристика Luma: при одинаковых входных данных она выбирает одинаковый вариант, отдавая дополнительный вес более раннему времени для важных и сложных дел. Требование «по возможности раньше» тем самым преобразовано в предпочтение, а не в жёсткий запрет позднего размещения. Жёстким ограничением основного пути остаётся вместимость в найденный свободный промежуток; окончательное поведение резервной ветви рассматривается отдельно как ограничение.

Для сложной задачи `SubtaskAutoScheduler` сначала вычисляет срочность каждой подзадачи из важности и сложности, задаёт ориентир внутри общего периода и последовательно подбирает свободные интервалы. После добавления очередного плана этот интервал становится занятым для следующих подзадач. Родительская задача сохраняется с границами от начала первой до конца последней подзадачи, а каждая подзадача получает `parentTaskId`. До подтверждения формы черновики подзадач существуют только в памяти интерфейса; после сохранения это отдельные сущности Core Data со структурной связью с родителем.

Построение свободных промежутков показано в листинге 3.2:

```swift
for interval in busy {
    if interval.start > cursor {
        gaps.append(ScheduleInterval(start: cursor, end: interval.start))
    }
    cursor = max(cursor, interval.end)
}
if cursor < segment.end {
    gaps.append(ScheduleInterval(start: cursor, end: segment.end))
}
```

*Листинг 3.2 — Выделение свободных промежутков между занятыми интервалами*

Этот фрагмент показывает базовый механизм исключения пересечений в основном пути: курсор последовательно перемещается к концу занятого интервала, а кандидаты создаются только в образовавшихся разрывах. Полный алгоритм оценки в основной текст не включается, поскольку его коэффициенты являются авторской эвристикой и лучше воспринимаются в виде краткого пояснения, а не длинного листинга.

После создания обычной задачи `AddTaskCoordinator` проверяет результат через `lateBoundary`. Если начало находится до 23:00, а окончание — после этой границы, появляется диалог с вариантами «Оставить как есть» и «Разделить». До выбора положительного действия разделение не выполняется. При согласии первая запись сокращается до 23:00, а остаток создаётся на следующий день с 08:00 и названием с пометкой «продолжение». При отказе сохраняется исходный вариант.

*Рисунок 3.2 — Запрос согласия на разделение задачи, пересекающей границу 23:00*

FR-05 подтверждено частично: формы и три вида элементов существуют, но для события короче 15 минут увеличивается расчётная `estimatedDuration`, тогда как введённая дата окончания не исправляется и запись не отклоняется. FR-06 и FR-07 также подтверждены частично. Основной путь не создаёт пересечений, однако резервный `nextNonOverlappingStart` не ограничивает результат концом дня и дедлайном; для сложной задачи резервное размещение имеет ту же границу. Сохранение родителя и подзадач не оформлено как единая транзакция.

FR-08 подтверждено частично. Согласие действительно запрашивается, но продолжение связано с первой частью только названием: `parentTaskId` при его создании равен `nil`. Сначала обновляется исходная запись, затем отдельной операцией создаётся продолжение; при ошибке второй операции возможен частичный результат. Нужны граничные тесты для длительности 15 минут, ровно 23:00, пустого периода, отсутствия свободного окна, дедлайна и ошибки сохранения. Исходники таких сценарных тестов не обнаружены, а существующий unit-test bundle не запускался.

## 3.4 Уведомления и дневник

FR-09 требует включать уведомления из профиля, запрашивать системное разрешение, сообщать об отказе, создавать напоминания о задачах за 30 и 5 минут, а для сложной задачи — по каждой подзадаче. Для дневника сна заданы моменты 08:00 и 12:00, для дневника эмоций — 18:00 и 20:00; после записи оставшиеся напоминания дня должны отменяться. Доставленные уведомления выводятся отдельным списком в обратной хронологии. FR-10 определяет два вида дневниковых записей и одну выбираемую за операцию эмоцию из перечня: радость, грусть, злость, тревога, покой и любовь. Для эмоции указываются интенсивность 1–10 и необязательная причина; для сна — время засыпания и пробуждения с автоматическим расчётом длительности.

`ProfileViewModel` передаёт изменение переключателя в `LocalNotificationService`. При первом включении сервис запрашивает у `UNUserNotificationCenter` разрешения `alert`, `sound` и `badge`. Если система возвращает отказ, переключатель сбрасывается, а модель представления выдаёт сообщение о необходимости изменить настройки iOS. При выключении очищаются все ожидающие и все уже доставленные уведомления приложения. Аналогичная полная отмена выполняется при выходе из учётной записи.

Для простой задачи создаются идентификаторы напоминаний на 30 и 5 минут до начала. Сложная задача предварительно раскрывается до подзадач. Если тридцатиминутный момент уже прошёл, такое уведомление не планируется. Если до старта осталось меньше пяти минут, код создаёт второе уведомление примерно через три секунды. Это осознанная резервная ветвь текущей реализации, но она не равна буквальному требованию «за 5 минут» и потому должна быть явно отражена в проверке.

Идентификатор напоминания включает UUID задачи и контрольный интервал, поэтому повторное планирование одного и того же напоминания предварительно удаляет запрос с тем же идентификатором. Это снижает вероятность дубликатов в обычном сценарии создания. Однако изменение времени задачи требует повторного вызова планирования, а удаление — вызова отмены. Само наличие стабильного идентификатора не связывает эти операции автоматически, что и объясняет отмеченное ниже расхождение между доступным методом отмены и фактическим календарным потоком.

Дневниковое расписание строится на семь ближайших дней. Перед добавлением уведомлений сервис проверяет наличие записи соответствующего типа. После успешного сохранения `DiaryViewModel` вызывает отмену только оставшихся напоминаний эмоций либо сна на текущий день. Экран истории получает доставленные уведомления от системного центра и сортирует их по убыванию даты. В DEBUG-сборке пустой список может быть заменён демонстрационными элементами, поэтому такой экран нельзя считать доказательством фактической доставки без отдельного прогона.

Эмоциональный дневник предоставляет одиночный выбор: `EmotionGridView` хранит один `selectedIndex`, а обработчик сохранения формирует один элемент ввода. Перечень в доменной модели точно совпадает с техническим заданием:

```swift
enum EmotionKind: String, CaseIterable {
    case joy = "Радость"
    case sadness = "Грусть"
    case anger = "Злость"
    case anxiety = "Тревога"
    case calm = "Покой"
    case love = "Любовь"
}
```

*Листинг 3.3 — Перечень эмоций, используемый дневником и анализом*

Проверка модели показала, что за одно сохранение пользователь выбирает одну эмоцию. Ранее указанная возможность выбора нескольких эмоций интерфейсом не поддерживается. Также в реализации нет эмоции «страх»: отрицательное направление имеют грусть, злость и тревога; положительное — радость, покой и любовь. Интенсивность при сохранении ограничивается диапазоном 1–10, причина может отсутствовать. `DiaryRepository` связывает запись с пользователем и календарным днём. Для сна время относится к выбранному дню, а пробуждение переносится на следующие сутки, если оно не позже времени засыпания; после этого длительность вычисляется в минутах.

FR-10 подтверждено кодом: типы записей, точный перечень, одиночный выбор, интенсивность, необязательная причина, переход сна через полночь и отмена дневниковых напоминаний прослеживаются по вызовам. FR-09 подтверждено частично. Планирование, настройки, история и общая отмена реализованы, но системная доставка и отказ разрешения требуют проверки на устройстве. При редактировании или удалении задачи в `CalendarViewModel` не найден явный вызов отмены либо перепланирования её старых напоминаний, хотя метод `cancelTaskReminders` существует. Дополнительной проверки требуют уведомление через три секунды, сортировка реальной истории и отсутствие демонстрационных записей в пользовательской сборке.

## 3.5 Фокус-сессия и Live Activity

FR-11 предусматривает выбор незавершённой задачи или подзадачи текущего дня, определение продолжительности по плановой оценке, выбор локального плейлиста либо режима без музыки, секундный обратный отсчёт, остановку воспроизведения, сохранение фактической длительности и завершение задачи. На поддерживаемом устройстве Live Activity должна показывать тип и название задачи и оставшееся время на экране блокировки и в Dynamic Island, позволять завершить задачу и закрываться после окончания сеанса. NFR-08 дополнительно требует освобождать таймер, музыку и активность.

`FocusViewModel` получает элементы текущего дня через тот же `TaskService`, что и календарь. Сложные задачи раскрываются до незавершённых подзадач. Для выбранного объекта создаётся `FocusTaskItem`, а продолжительность определяется по `estimatedDuration`; если она отсутствует, используется разница между концом и началом, с нижней границей одна минута. Локальные плейлисты перечислены в `FocusMusicLibrary`, воспроизводятся `FocusMusicPlayer`, а режим без музыки не вызывает проигрыватель.

После старта `FocusViewController` сохраняет время начала и окончания, запускает `Timer` с периодом одна секунда и просит `FocusLiveActivityManager` создать системную активность. Если ActivityKit недоступен или запрос завершился ошибкой, обычный таймер продолжает работу. При завершении контроллер инвалидирует таймер, скрывает карточку отсчёта, завершает Live Activity, останавливает музыку, сохраняет фактический интервал фокус-сессии и отмечает локальную задачу выполненной.

Сохранённая фокус-сессия отделена от плановой длительности задачи. В запись попадают фактические моменты начала и окончания, а репозиторий достижений использует их разницу при пересчёте накопленного времени. Поэтому досрочное завершение не приписывает пользователю всю запланированную продолжительность. Одновременно задача завершается только один раз: при возврате из Live Activity экран получает уведомление и завершает локальное состояние сеанса без повторного изменения задачи.

Расширение Live Activity реализовано на SwiftUI. На экране блокировки оно показывает название и тип задачи, таймер и действие завершения; для Dynamic Island определены развёрнутое, компактное и минимальное состояния. Действие формирует внутреннюю ссылку с идентификатором задачи. `AppCoordinator` проверяет активную сессию, завершает задачу через `TaskService`, закрывает активность и сообщает экрану фокуса, чтобы тот не повторял операцию завершения.

*Рисунок 3.3 — Фокус-сессия Luma и соответствующая Live Activity на экране блокировки и в Dynamic Island*

На составном рисунке следует показать совпадение названия, типа и оставшегося времени между приложением и системным интерфейсом, а также доступность действия «Завершить задачу».

FR-11 подтверждено частично. Таймер, музыка, запись сессии, код расширения и обработка внутренней ссылки существуют, а приложение и расширение успешно скомпилированы вместе. Однако `TaskService.fetchTasks` объединяет внутренние задачи с событиями системного календаря, и `FocusViewModel` не исключает источник `.calendar`. Такое событие можно выбрать для фокуса, но `setCompleted` ищет локальную сущность и не может изменить EventKit. Следовательно, системные события не должны описываться как полноценно завершаемые объекты; их необходимо исключить из списка или явно сделать действие завершения недоступным.

Фактическое отображение на экране блокировки, варианты Dynamic Island, переход по ссылке из заблокированного состояния и поведение при сворачивании требуют испытания на поддерживаемом устройстве. Обычный путь завершения останавливает ресурсы, но уничтожение экрана само по себе не вызывает явного завершения Live Activity. Поэтому NFR-08 подтверждено только частично, а отсутствие утечек и корректность принудительного прерывания должны проверяться инструментально.

## 3.6 Анализ дня, статистика и достижения

FR-12 требует анализировать задачи сегодня и завтра, сон, эмоциональные записи, просрочки и занятое системными событиями время. Результат включает ресурс, нагрузку, баланс, уровень нагрузки, уверенность и не более четырёх рекомендаций. При недостатке данных анализ должен называться предварительным. FR-13 задаёт недельные показатели и подробную статистику эмоций, сна и задач за соответствующие периоды. FR-14 описывает каталог достижений, состояния `locked`, `unlocked` и `opened`, обновление прогресса по задачам, дневнику и фокус-сессиям, начисление 50 единиц опыта и новый уровень каждые 250 единиц.

`AnalysisService` собирает пользователя, записи дневника, задачи текущего и следующего дня и передаёт их в `UserAnalysisEngine`. Сложная задача раскрывается до подзадач. Внешние календарные события участвуют в оценке занятого времени как фиксированные интервалы, но не входят в гибкое усилие пользователя. Отдельно вычисляются текущий и семидневный сон, эмоциональное состояние, оставшиеся и завершённые элементы, просрочки, доступное время и нагрузка следующего дня.

Текущая версия алгоритма не использует прежнее базовое значение 86. Ресурс строится из доступных компонентов: оценки сна с весом 0,65 и эмоционального ресурса с весом 0,35; если обе группы данных отсутствуют, используется нейтральное значение 50. Нагрузка дня рассчитывается из взвешенной длительности гибких задач, уже затраченного усилия, просрочек и фрагментации списка с учётом времени, занятого внешними событиями. Баланс получается из разности ресурса и нагрузки. Значения ограничиваются шкалой 0–100. Уверенность зависит от наличия даты рождения, записи сна, нескольких записей сна за неделю и эмоциональной записи. При низкой уверенности итог помечается как предварительный.

Эмоциональная часть использует тот же `EmotionKind`, что и дневник. Интенсивность умножается на направление эмоции: радость, покой и любовь поддерживают ресурс, а грусть, злость и тревога увеличивают напряжение. Поэтому раннее описание со «страхом» было ошибочным. Конкретные веса и пороги являются авторской эвристикой приложения, а не нормативными медицинскими показателями. Модуль формирует пользовательскую подсказку для самоорганизации и не выполняет диагностику состояния здоровья.

Обработку нехватки данных показывает результирующая ветвь анализа:

```swift
let readinessScore = confidenceLevel == .low
    ? resourceScore
    : balanceScore

if confidenceLevel == .low {
    return "Предварительный анализ: данных пока недостаточно. \(sleepText), задач — \(workText)."
}
```

*Листинг 3.4 — Выбор итоговой оценки и маркировка предварительного анализа*

Экран общей статистики получает из `AnalysisService.weeklyStats` количество выполненных и общее количество задач, качество сна, эффективность и эмоциональный показатель за семь дней. Эффективность учитывает длительность, сложность и важность завершённых элементов. Подробные представления показывают 30-дневное распределение эмоций и задач, сведения о сне и состав завершённых и незавершённых задач выбранного дня. После уведомлений об изменении задач или дневника соответствующие модели представления перезагружают данные.

Для недельных показателей используются сохранённые записи в интервале от начала дня шесть суток назад до начала следующих суток. Качество сна сравнивает длительность с возрастным рекомендуемым диапазоном; эффективность является долей взвешенного объёма завершённых задач; эмоциональный показатель переводит средний баланс из диапазона от −1 до 1 в диапазон от 0 до 1. Эти формулы воспроизводимы по коду, однако их численные результаты должны проверяться заранее подготовленными наборами данных, особенно на границах недельного окна.

`AchievementRepository` при первом обращении создаёт каталог достижений, затем пересчитывает метрики по завершённым задачам, уникальным дням дневника, продолжительности сна, интенсивным эмоциональным дням и накопленному времени фокуса. Выполненное условие переводит достижение из заблокированного в разблокированное состояние; пользовательское открытие устанавливает `opened`. `AchievementLevelProgress` считает только открытые достижения: каждое даёт 50 единиц опыта, каждые 250 единиц повышают уровень, а звание выбирается из заданного ряда. Уровень, звание и доля следующего уровня отображаются в достижениях и профиле.

FR-12 подтверждено кодом. Для `UserAnalysisEngine` существуют содержательные модульные тесты, охватывающие отсутствие данных, выполнение задач, смешанные эмоции, перегруз, сон, возрастные диапазоны и календарные события. При этом наличие тестовых методов не следует путать с их выполнением в рамках данной проверки: unit-test bundle успешно скомпилирован, но набор не запускался из-за отсутствия Test action в shared-схеме.

FR-13 и FR-14 подтверждены частично. Формулы, экраны и переходы состояний найдены, но недельные и 30-дневные границы, смена часового пояса, повторный пересчёт, границы уровня и численная сверка агрегатов не покрыты подтверждённым прогоном. Для достижений важно различать «разблокировано» и «открыто»: опыт начисляется после открытия, а не сразу при выполнении условия. Это поведение соответствует реализации и должно проверяться отдельными сценариями.

## 3.7 Трассировка требований и результаты проверки

NFR-10 требует модульной проверяемости логики и автоматизации основных сценариев, а остальные FR и NFR задают конкретные функциональные, аппаратные и количественные критерии. Для итоговой трассировки необходимо различать наличие реализации, успешную компиляцию и фактическое выполнение испытания.

Проверка выполнена по текущему рабочему дереву в трёх формах. Во-первых, проведена статическая инспекция связей между моделями представления, сервисами, репозиториями, доменными алгоритмами и системными API. Во-вторых, выполнена сборка: приложение Luma и расширение Live Activity собраны успешно при отключённой подписи и командном override ограничения пользовательских скриптов; отдельно успешно скомпилирован unit-test bundle. В-третьих, была предпринята попытка штатного запуска тестов, но shared-схема не настроена для Test action. Поэтому результата выполненного набора тестов нет. Такой исход не означает падение тестов: тестовые методы не запускались.

Проверяемым объектом было текущее состояние рабочего дерева, включая незакоммиченные изменения. Сборочные продукты создавались вне проекта, а исходный код и настройки схемы во время проверки не изменялись. Успешная компиляция подтверждает согласованность типов, подключение расширения и возможность собрать тестовый target в использованной конфигурации. Она не подтверждает корректность алгоритмических результатов, системных разрешений, уведомлений, фонового выполнения и поведения на конкретных устройствах; для этих выводов нужны отдельные протоколы с версией ОС, моделью устройства, входными данными и ожидаемым результатом.

*Таблица 3.1 — Компактная матрица трассировки требований к реализации и проверке*

По результатам статической инспекции из четырнадцати функциональных групп четыре подтверждены кодом, а десять подтверждены частично. Из десяти нефункциональных групп одна подтверждена кодом, восемь подтверждены частично, одна требует runtime-испытания. Эти числа характеризуют найденные свидетельства, а не процент готовности и не результат приёмки. Нулевого программного покрытия не обнаружено: для каждой укрупнённой группы существует хотя бы часть механизма, но у составных требований остаются неподтверждённые либо расходящиеся ветви.

Основные экраны готового приложения реализованы, однако остаются ограничения в граничных сценариях и в полноте проверки. Для планирования это резервное размещение вне 23:00 или дедлайна и нетранзакционное разделение; для уведомлений — старые запросы после изменения или удаления задачи; для фокуса — доступность внешнего события, которое нельзя завершить; для хранения — подавление части ошибок; для качественных требований — отсутствие измерений и аппаратной матрицы. Исправление этих пунктов и настройка Test action необходимы для последующего вывода о полном соответствии, но не входят в формулировку уже полученного результата: разработано готовое приложение Luma, приложение и расширение Live Activity успешно компилируются, unit-test bundle компилируется, а выполнение тестов в проведённой проверке не состоялось.
