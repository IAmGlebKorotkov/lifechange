# Доказательная база по исходному коду Luma

Дата проверки: 25 сентября 2026 г.

## 1. Область и метод проверки

Проведена независимая статическая инспекция текущего рабочего дерева с сопоставлением требований из `requirements.md`, описания реализации P0150–P0303 и таблицы 18 из `coursework-corrected.md`, а также матрицы из `traceability-and-uml.md` с файлами и символами исходного кода.

Статическая инспекция кода **не является приёмкой**. Статус «подтверждено кодом» означает, что требуемая ветвь поведения явно реализована и прослеживается по вызовам; поведение системных API, отображение на реальном устройстве и временные характеристики всё равно требуют испытаний.

Для краткости ниже используются обозначения:

- `<APP>` — каталог исходников основного target приложения;
- `<LA>` — `FocusLiveActivityExtension/Sources`;
- `<UT>` — каталог исходников target модульных тестов;
- `<UIT>` — каталог исходников target UI-тестов.

Рабочее дерево на момент проверки содержит пользовательские незакоммиченные изменения. Инспекция описывает именно это состояние; исходный код и настройки проекта в ходе проверки не изменялись.

## 2. Итоговая оценка

Из 14 функциональных требований 4 подтверждены кодом, 10 подтверждены частично. Из 10 нефункциональных требований 1 подтверждено кодом, 8 подтверждены частично, 1 требует runtime-испытания. Требований, для которых не найдено вообще никакой реализации, нет, однако внутри составных требований обнаружены отсутствующие или неподтверждённые ветви.

Главные расхождения:

- интерфейс дневника сохраняет ровно одну эмоцию из шести за одну операцию; формулировка P0271 о выборе «одной или нескольких» эмоций не соответствует коду и исходному требованию;
- отключение уведомлений и выход отменяют ожидающие и удаляют доставленные локальные уведомления, но удаление/редактирование задачи не сопровождается явной отменой или перепланированием её прежних напоминаний;
- разделение задачи после 23:00 выполняется только после явного согласия, однако продолжение связано с исходной задачей лишь названием, а операция сохранения не транзакционна;
- Live Activity реализована, включая завершение по deep link, но внешнее календарное событие можно выбрать в фокусе, хотя отметить его выполненным приложение не может;
- календарные события читаются и обновляются, методов записи в EventKit не найдено;
- пароль хешируется с индивидуальной солью-UUID и хранится в Keychain, но ошибки записи Keychain и Core Data не доводятся до вызывающего слоя;
- приложение не содержит сетевого клиента и основные данные локальны, но полноценная автономность и восстановление после прерываний не покрыты испытаниями;
- содержательные unit-тесты существуют только для анализа, обработчика действий уведомлений и отдельных UI-компонентов; UI-тесты фактически являются smoke-запусками без проверок пользовательских сценариев.

## 5. Адресная проверка спорных функций

### Одна эмоция и перечень

`EmotionKind`, `EmotionPalette.all`, модель выбора `EmotionGridView.selectedIndex` и передача одного элемента из `EmotionDiaryView.saveTapped` согласованно задают одну выбранную эмоцию. Перечень состоит ровно из шести значений: радость, грусть, гнев, тревога, спокойствие, любовь. Это соответствует FR-10 и противоречит только расширенной формулировке P0271 о нескольких эмоциях за одно заполнение.

### Уведомления, история и выход

Планирование 30/5 минут и дневниковых окон реализовано. История берётся через `UNUserNotificationCenter.getDeliveredNotifications` и сортируется по дате, но DEBUG-подмена пустого результата демонстрационными строками не позволяет считать такую сборку чистой историей фактически доставленных уведомлений. `AppCoordinator` при подтверждённом выходе вызывает `SessionManager.logout()` и `cancelAllScheduledNotifications()`, который удаляет pending и delivered notifications. Системную доставку и поведение разрешений нужно проверять динамически.

### Разделение после 23:00

Вызов `splitTaskAtLateBoundary` расположен только в положительной ветви alert-действия «Разделить». Автоматического разделения до согласия не найдено. Продолжение начинается на следующий день в 08:00, но не связано с первой частью идентификатором/отношением и создаётся отдельной операцией после изменения первой записи.

### Live Activity и завершение задачи

Расширение показывает название, тип и остаток времени в Lock Screen/Dynamic Island. Нажатие завершения ведёт по custom URL в `AppCoordinator.handle(url:)`, который завершает локальную задачу и Live Activity; экран фокуса получает уведомление и сохраняет сессию. Runtime-проверка нужна для системного UI, фонового состояния и блокировки экрана. Системные события следует исключить из списка выбираемых объектов либо явно сделать для них недоступным завершение.

### Системный календарь

В `CalendarEventService` найдены только запрос доступа и чтение событий. Обновление инициируется изменением EventKit и возвратом приложения в active. Методов записи не найдено, поэтому read-only-поведение подтверждено статически; разрешения и обновление — частично, до runtime-проверки.

### Хеш, соль и Keychain

Репозиторий создаёт UUID пользователя до записи пароля и передаёт его как индивидуальную соль; `KeychainManager` вычисляет SHA-256 по паролю и соли и кладёт только хеш в Keychain. Пароль/хеш отсутствуют в модели Core Data. Криптографическая и отказоустойчивая часть неполна: статусы Keychain не становятся ошибкой доменного слоя, а соль является публичным UUID, а не отдельно сгенерированным секретом.

### Автономность

HTTP-клиента и обязательных внешних сервисов нет; Core Data, локальные уведомления и bundled media обеспечивают основной офлайн-контур. EventKit при отсутствии доступа деградирует до пустого набора системных событий. Это сильное статическое свидетельство, но не замена испытанию в airplane mode и после убийства/перезапуска процесса.

## 6. Сборка и тесты

Команды выполнялись без изменения проекта; Derived Data и продукты направлялись в `/tmp`.

1. `xcodebuild -list -project <project>` — успешно: обнаружены основной app-target, расширение Live Activity, unit- и UI-test targets, основная shared-схема и схема расширения.
2. Обычная generic iOS build в ограниченной среде сначала завершилась ошибкой обработки asset catalog из-за недоступных simulator runtimes.
3. Повторная generic iOS device build вне ограничения симуляторов дошла до build phase SwiftLint, но её остановил Xcode User Script Sandbox при чтении файла конфигурации линтера.
4. Та же сборка с командным override `ENABLE_USER_SCRIPT_SANDBOXING=NO` и `CODE_SIGNING_ALLOWED=NO` завершилась `** BUILD SUCCEEDED **`; собраны приложение и расширение Live Activity. Проектные настройки не менялись. SwiftLint выдал предупреждения, в том числе об empty XCTest method.
5. `xcodebuild ... test` для основной shared-схемы не запустил тесты и завершился с exit code 66: схема «is not currently configured for the test action».
6. Отдельная сборка unit-test target для `iphonesimulator` завершилась `** BUILD SUCCEEDED **`. Это подтверждает компиляцию test bundle, но не выполнение тестовых методов.

Итого: компиляция приложения, расширения и unit-test bundle подтверждена. Результата выполненного набора тестов нет, потому что Test action shared-схемы не настроен. Для воспроизводимого CI-прогона нужно добавить testable targets в схему или test plan; это отдельное изменение проекта и в рамках данной проверки не выполнялось.
